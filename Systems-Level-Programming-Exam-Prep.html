Part A — Key concepts

1. What systems-level programming is, and why it matters

Systems-level programming is the missing link between assembly (very low-level) and Java/Python (very high-level): Hardware → Assembly → C → Java/Python.

  • Abstraction level: the more irrelevant detail a language hides, the higher-level it is. A higher-level language usually turns one statement into more opcodes than a lower-level one.
  • C is a high-level language defined by an ISO standard (ISO/IEC 9899). C hides registers, opcodes, flags, stack setup and teardown, calling and register conventions, interrupts, syscalls, addressing modes and instruction sets. It does not hide memory or memory areas (.text, .data, .bss). Those stay your problem.
  • Why learn it: (1) it's interesting; (2) it shows how machines and operating systems work, which helps you answer "why is my program slow?" and "why does this optimisation work?"; (3) you can't write systems software without it. POSIX is specified in C.

3. Undefined behaviour (UB)

Definition (C standard): behaviour, on use of a non-portable or erroneous construct or erroneous data, for which the standard imposes no requirements.

Example: signed integer overflow. "No requirements" means the implementation may:

  • ignore the situation completely, often with unpredictable results;
  • behave in a documented, environment-specific way, with or without a diagnostic;
  • stop translation or execution with a diagnostic;
  • …or do anything else.

Common sources of UB: writing to a string literal, freeing memory that wasn't dynamically allocated, reading or writing past the end of an array, dereferencing NULL or freed pointers, and mismatched types across object files.

4. The three fundamental rules of C

  1. All data has a place (in memory).
  2. All data has a size (in bytes).
  3. Zero is special.
Break any of these and you get undefined behaviour.
Copy-by-value only. C never passes by reference. When you call a function, each argument's value is copied into the parameter variable, then the function runs. Assignment also copies the value. To let a function change a caller's variable, pass a pointer (the copied value is then an address). C syntax can be deceptive: many things that look like built-in operations are really "pseudo-instructions" for memory operations.

5. Where data lives: stack, heap and data segment

Static allocation means the size is known at compile time (an int, a fixed-size array). Dynamic allocation means the size is only known at run time (reading n integers, where n comes from the user). C makes you manage the dynamic kind.

All data is in exactly one of these places:

AreaAccessLifetimeWhat goes there
StackRead-writeCreated at function-call setup, destroyed at teardownLocal variables, parameters, fixed-size local arrays. Size must be known at compile time.
HeapRead-writeFrom malloc/calloc/realloc until free (memory is obtained from the OS by a syscall)Data whose size is not known at compile time
Data segmentString literals and constants are read-onlyThe whole run of the programString literals, constants, globals and static variables

Function code lives in the .text (code) section, which the slides group with the "data segment / other in-process section".

Watch out: one slide says global variables are reserved "on the stack". In reality globals (and static locals) live in the data segment (.data/.bss), and only locals and arguments go on the stack. In the exam, put globals such as errno in the data segment.

6. Sizes and sizeof

  • The type of data determines its size. sizeof(char) is 1 by definition, which is almost always one byte. Every other size is measured in char units.
  • Typical x64 sizes: char 1 · short 2 · int 4 · float 4 · long 8 · double 8 · any pointer 8. (On 32-bit x86, pointers and long are usually 4.)
  • signed and unsigned don't change size.
  • sizeof(v) or sizeof(int) returns a size_t, an unsigned type that is usually unsigned long.
  • For a static array, sizeof gives the total bytes, not the element count. Element count = sizeof(a)/sizeof(a[0]).
  • For a pointer, sizeof gives the pointer's size (8 on x64), never the size of what it points to.
  • A cast forces C to treat X as Y, which trades type safety for flexibility.

7. Pointers

A pointer is a variable that stores a memory address. The address is where the data starts.

  • Address-of &v gives the address of v. If v is a T, then &v is a T*.
  • Dereference *m gives the value at address m ("following" the pointer).
  • All pointers are the same size, which depends on the largest address the machine can use. On x64 that's 8 bytes (64-bit addresses).
  • You can have pointers to pointers: int**.
Operation on int *kSyntaxMeaning
Assignk = &x;Change the stored address
Read the addresskLook at the address itself
Dereference*kValue at that address
Arithmetick+1Moves in units of sizeof(int). If k = …19010, then k+1 = …19014
Indexk[i]Same as *(k+i)
Address of the pointer&kAn int**
void* (void pointer): a raw address with no type.
  • You can't dereference it, because C doesn't know how to interpret the memory.
  • You can't index it or do pointer arithmetic, because the element size is unknown.
  • Cast it first: *((int*)p), or ((node*)v)->name.
Choosing the operator: Is it a void*? Cast, then dereference. Is it a pointer? Use *v or v->field. Is it a plain value? Use v or v.field.
Function pointers: int (*f)(char, char) declares f as a pointer to a function that takes (char, char) and returns int. Call it as f('a','b').
Multi-level: char **m is a pointer to pointer to char, i.e. an array of strings. int **xs is a table or matrix. You must allocate each level separately. Drawing arrow diagrams helps.

8. Endianness

int v = 123456789; is 0x075BCD15, i.e. the bytes 07 5B CD 15.

OrderBytes in memory, starting at &v
Big-endian (most significant byte first; how we write numbers)07 5B CD 15
Little-endian (least significant byte first; x86/x64)15 CD 5B 07

&v always points at the lowest address, so the same int looks different byte by byte on machines with different endianness. The union exam question tests exactly this.

9. Zero is special

  1. In conditionals, non-zero is true and zero is false.
  2. Zero marks the end of data with unknown or dynamic size. Used this way it is called a terminator or sentinel, and it means "stop reading, you've reached the end".

Each kind of type has its own zero: '\0' is the char zero (NUL), 0 is the numeric zero, and NULL is the pointer zero.

10. Arrays and strings

Strings: a C string is a sequence of chars ending in '\0'. Instead of copying the whole string, you copy a pointer to its first char.
char *r = "testing"; puts a pointer r on the stack. It points to t e s t i n g \0 in the data segment, which is read-only, so writing to it is UB.
Static arrays (elements stored one after another):
  1. Allocated on the stack (when local).
  2. Must get a size at creation. Explicitly: int a[3]. Implicitly: double b[] = {9.5, 87.2, -32.6, 5.0} has length 4, and char c[] = "hello" has length 6 because of the '\0'.
  3. sizeof gives the total bytes. That only equals the element count for char arrays.
  4. The element count is lost when the array is passed to a function, because only a pointer to element 0 is passed. The array decays to a pointer.
  5. So you usually pass the size as an extra parameter.
Array vs pointer: char k[20] = "yellow"; copies the characters into a 20-byte stack array, and you can modify them. char *m = "green"; is only an 8-byte pointer on the stack to a read-only literal.

11. Dynamic memory (<stdlib.h>)

FunctionWhat it does
malloc(bytes)Allocates bytes of uninitialised memory
calloc(count, size)Allocates count × size bytes, all set to zero
realloc(p, bytes)Grows or shrinks a block (it may move it). If p is NULL it acts like malloc
free(p)Returns the memory. Freeing memory that was not dynamically allocated is UB

They all return void*, and NULL on failure, so always check.

int *z = (int*)malloc(sizeof(int) * 10);
int *z = (int*)calloc(10, sizeof(int));
z = (int*)realloc(z, sizeof(int) * 15);
free(z);
Common bugs: forgetting free (memory leak); not checking for NULL; using memory after free; freeing twice; malloc(n) instead of malloc(n * sizeof(T)).

12. const

const int days_per_week = 7; means the value can't be changed. With pointers, what is constant depends on where const sits. A tip: read the declaration right to left.

Note: the slide writes the constant pointer as int const *x, which is a typo. In real C, int const *x means the same as const int *x. A constant pointer needs const after the *: int * const x. Learn the meanings and use the correct syntax.

13. User-defined types: struct, union, enum, typedef

At run time, types don't exist. They are replaced by memory operations at fixed offsets. Defining a type reserves no memory, and the compiled program doesn't change. Defining a variable of that type reserves memory.

Declaration vs definition
  • A declaration gives a name and type, e.g. a function prototype int f(int); or extern int g;.
  • A definition gives a name and type and reserves memory, e.g. a function with its body, or a variable.
struct: members placed one after another. 
struct node {
  void *data;
  struct node *next;
};
struct node x;   /* 8+8 = 16 on x64 */
Size is the sum of the members, plus padding.
union: every member starts at the same address. 
union integer {
  unsigned int   value;
  unsigned short words[2];
  unsigned char  low_word[2];
};  /* max(4,4,2) = 4 */
Size is the largest member. Use it to view the same memory in different ways.
enum: links integers to names. 
enum day { WEEKEND, HOLIDAY, WORKDAY };
/*          0        1        2     */
typedef: gives a type a shorter name. 
typedef struct node_t {
  void *data;
  struct node_t *next; /* can't use 'node' yet */
} node;                /* new name goes last */

Member access: s.field on a value. On a pointer, (*p).field is the same as p->field.

Alignment and padding: memory is read in CPU-word chunks, and aligned accesses are fastest. 32-bit machines align to 4 bytes and 64-bit machines to 8, so the compiler may add padding. Order struct members by descending size to minimise padding. (The course mostly ignores alignment, but it exists.)

14. Reading complex declarations: "march forward unless forced backwards"

  1. Start at the identifier and write "name is".
  2. Go right:
    • [] → "an array of"; [N] → "an array of N"
    • () or (void) → "a function taking nothing, returning"
    • (…) → "a function taking (decode each parameter), returning"
    • At the end, or at an unmatched ), go to step 3
  3. Go left:
    • ( → go back to step 2
    • * const → "a constant pointer to"; * → "a pointer to"
    • const followed by a type → "constant type", then stop; a type on its own → write it down and stop

See Q10 for the two worked examples from the slides.

15. Building programs: compilation and linking

You can build either an executable or a library. The only difference is that an executable has an entry point (main). Larger systems use a build system (e.g. make) instead of compiling by hand.

#StepInput → outputWhat happens
1Preprocessing.c → preprocessed .cText transforms: comments become whitespace, #include is pasted in, macros are expanded, #if blocks are kept or dropped
2Compilation→ assembly (.s)Each preprocessed file becomes assembly language
3Assembly→ object code (.o)The assembler produces machine-specific native code plus relocation information. Object code is not executable
4Linking.o files + libraries → executable or libraryThe linker resolves symbols: internal symbols to their definitions, external ones to libraries. A runtime linker fills deliberate gaps later (LD_PRELOAD on Linux)
Preprocessor directives
  • #include: copy the file's contents in here. <stdio.h> searches the system include paths. "stdio.h" searches the current or project directory first, then the system paths.
  • #define: defines a macro (text substitution).
  • #ifdef / #ifndef … #else … #endif: include or skip text depending on whether a macro is defined. This is used for include guards. #else is optional.
  • #pragma: compiler-specific; ignored if the compiler doesn't recognise it.
Header files (.h) hold declarations (prototypes) of what exists in other files. They can also declare variables, and .c files refer to those with extern. If different object files assume different types for the same name, the result is UB.

16. Command-line arguments

int main(int argc, char **argv)   /* instead of int main(void) */

argc is the number of arguments and argv is an array of strings. argv[0] is always the name used to start the program. The return type is still int.

Q1 — Struct, union, typedef and #include

#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

struct bytes {
  unsigned char fourth;
  unsigned char third;
  unsigned char second;
  unsigned char first;
};

typedef union number {
  struct bytes bytes;
  unsigned int n;
} num;
Is struct bytes a definition or a declaration? What's the difference?

It is a type definition: it names the type and gives its full layout (four unsigned char members), so the compiler knows its size. A bare struct bytes; would only be a (forward) declaration, an incomplete type you can't create variables of.

Declaration = name + type. Definition = name + type + it can occupy memory. Defining a type still reserves no memory. Memory is only reserved when you define a variable of that type (e.g. struct bytes b;).

What does the typedef allow us to do?

We can write num x; instead of union number x;. num is just a shorter alias for the type union number. It doesn't create a new type or change the compiled code.

What is the size of a struct bytes on x86? On x64?

4 bytes on both. It holds four 1-byte unsigned chars, and a char is 1 by definition on every platform. char needs only 1-byte alignment, so there is no padding. Word size (32 vs 64-bit) doesn't matter because there are no pointers or longs.

What is the size of num on x86? On x64?

4 bytes on both. A union is as big as its largest member: max(sizeof(struct bytes), sizeof(unsigned int)) = max(4, 4) = 4. unsigned int is 4 bytes on both x86 and x64.

What do the #include directives do? What's the difference between <stdio.h> and "stdio.h"?

#include is a preprocessor directive. It copies the named file's contents into this spot before compilation. Here that brings in the declarations (prototypes) for printf/fgets (stdio.h), malloc/strtol/free (stdlib.h) and errno (errno.h).

  • <stdio.h> searches only the system/standard include directories. Use it for library headers.
  • "stdio.h" searches the current/project directory first, then falls back to the system directories. Use it for your own headers.

Q2 — Where is each thing stored?

static int readInt(const char* prompt, unsigned int* result) {
  char input[16];
  char *end;
redo:
  printf("%s\n", prompt);
  if (fgets(input, 16, stdin) == NULL) {
    return -1;
  }
  errno = 0;
  *result = (unsigned int)strtol(input, &end, 10);
  if (errno != 0 || end == input) {
    goto redo;
  }
  return 0;
}
Where is input? Where is *input?

input is a fixed-size local array (char[16]), so all 16 bytes are on the stack, in readInt's frame. *input is input[0], the first char of that array, so it is also on the stack. (An array is not a pointer: there is no separate pointer variable pointing somewhere else.)

Where is readInt?

It's a function, so its machine code is in the code (.text) section, a read-only in-process section that exists for the whole run. That's the "data segment / other in-process section" bucket, not the stack or heap. static here means internal linkage: only this .c file can see it.

Where is result? Where is prompt?

Both are parameters, so they are on the stack. Each is a pointer (8 bytes on x64) holding a copy of the address the caller passed (copy-by-value).

(Trick question) Where is *result? Where is *prompt?

You can't tell from readInt alone. It depends on what the caller passed. A pointer can point into any of the three areas.

  • In this program, main calls readInt("Enter an integer", &(v->n)), where v came from malloc, so *result is on the heap. If someone passed &localVar, it would be on the stack.
  • *prompt is the first character of the string literal "Enter an integer", so it's in the data segment (read-only). That's also why the parameter is const char*.
Where is end?

end is a local char*, so it's on the stack. After strtol(input, &end, 10) it points to the first character in input that wasn't part of the number, so it points into the stack too. We pass &end (a char**) so that strtol can change our pointer.

Where is errno?

errno is a global error variable declared in <errno.h>, so it's in the data segment and lasts the whole program. (Technically it's thread-local in modern C, but "global, data segment" is the expected answer.) It shows C's error handling without exceptions: set errno = 0, call the function, then check whether errno != 0. The function also returns -1 to signal failure.

Q3 — The -> operator

static void reverse(struct bytes *v) {
  unsigned char tmp = v->first;
  v->first = v->fourth;
  v->fourth = tmp;
  tmp = v->second;
  v->second = v->third;
  v->third = tmp;
}
What does the -> syntax do? Why do you need it?

p->field dereferences the pointer, then accesses the member. It's shorthand for (*p).field. We need it because v is a pointer to a struct, not a struct, so v.first won't compile. We need a pointer because C is copy-by-value. If reverse took a struct bytes by value, it would swap the bytes of a copy, and the caller would never see the change.

Can you rewrite it using different syntax?

Yes. Use explicit dereference plus the dot operator (the brackets are needed because . binds tighter than *):

static void reverse(struct bytes *v) {
  unsigned char tmp = (*v).first;
  (*v).first  = (*v).fourth;
  (*v).fourth = tmp;
  tmp = (*v).second;
  (*v).second = (*v).third;
  (*v).third  = tmp;
}

Or use indexing: v[0].first is the same as (*(v+0)).first.

Q4 — main with malloc and the union

int main(void) {
  num *v = (num*)malloc(sizeof(num));
  if (readInt("Enter an integer", &(v->n)) != 0) {
      return -1;
  }
  printf("v = %u (decimal), %x (hexadecimal)\n", v->n, v->n);
  printf("bytes: %x %x %x %x\n", v->bytes.first, v->bytes.second,
      v->bytes.third, v->bytes.fourth);
  reverse(&(v->bytes));
  printf("Swapped!\n");
  printf("v = %u (decimal), %x (hexadecimal)\n", v->n, v->n);
  printf("bytes: %x %x %x %x\n", v->bytes.first, v->bytes.second, v->bytes.third, v->bytes.fourth);
  return 0;
}
Why do we cast the return of malloc?

malloc returns a void*, a raw address with no type, because it doesn't know what you'll store. The cast (num*) says "treat this memory as a num". It documents intent and makes the type explicit (and it's required in C++). In C, void* converts to other pointer types implicitly, so the cast is good style rather than strictly required.

If a tutor changes &(v->n) to v, the code still works. Explain why.

In a union, every member starts at the same address, the start of the union. So &(v->n) (the address of member n) is numerically the same as v (the address of the union). readInt only receives an address and writes 4 bytes there, so the same bytes get written. Only the pointer types differ (num* vs unsigned int*), and C's weak typing lets that through, at most with a warning.

Why does v->bytes.first use a -> and a .?

v is a pointer to a union, so we use -> to reach its member bytes. But bytes is a struct value stored inside the union, not a pointer, so we use . to reach first. Rule: use -> on pointers and . on values. In full: (*v).bytes.first.

Can I replace &(v->bytes) with v? Even if I could, why wouldn't I?

It would work, for the same reason as before: bytes is at offset 0 of the union, so both are the same address. But you shouldn't, because:

  • It's a type mismatch (num* passed where struct bytes* is expected). You throw away type safety and get a compiler warning.
  • It's misleading: the reader can't see you mean the bytes view of the number.
  • It's fragile: it only works because of the union's layout. If num became a struct, or bytes weren't first, it would silently break (UB).
There's a problem in main. What is it?

Memory leak: v is allocated with malloc but never freed, neither on the normal path nor on the early return -1. Also, the malloc result isn't checked for NULL. If allocation fails, &(v->n) dereferences NULL, which is UB.

num *v = (num*)malloc(sizeof(num));
if (v == NULL) return -2;
if (readInt("Enter an integer", &(v->n)) != 0) { free(v); return -1; }
...
free(v);
return 0;

Related point: on little-endian x86, first…fourth are declared in reverse order, so fourth holds the least significant byte. reverse swaps the byte order, which converts between little- and big-endian.

Q5 — calloc, error codes and addUp

static long addUp(int* arr, int n) { /* elided */ }

int main(void) {
    int n;
    if (readInt("Number of values to read?", &n) != 0 || n <= 0) return -1;
    int* values = (int*)calloc((size_t)n, sizeof(int));
    if (values == NULL) return -2;
    for (int i = 0; i < n; i++) readInt("Value?", values+i);
    printf("Added up to %lu\n", addUp(values, n));
    free(values);
    return 0;
}
What does each parameter to calloc mean?

calloc(count, size): the first is the number of elements (n) and the second is the size of each element in bytes (sizeof(int)). It allocates count × size bytes on the heap and sets them all to zero.

Why cast n to a size_t in the calloc call?

calloc's parameters have type size_t, an unsigned type (what sizeof returns). n is a signed int. The explicit cast makes the signed-to-unsigned conversion visible and avoids a compiler warning. It's safe only because we already checked n > 0. A negative int converted to size_t becomes a huge positive number.

Why return different values at different points?

C has no exceptions, so the return value is the error code. The program's exit status tells the caller (e.g. the shell) what went wrong: 0 = success, -1 = couldn't read a valid count, -2 = memory allocation failed. Different codes let you tell the failure causes apart.

When would values be NULL?

When allocation fails: the OS can't supply n × sizeof(int) bytes, e.g. you're out of memory or n is huge. malloc, calloc and realloc all return NULL on failure. Using NULL would be UB, hence the check.

Explain values+i in the call to readInt.

It's pointer arithmetic. values is an int*, so values+i moves forward i × sizeof(int) bytes, giving the address of element i. It's the same as &values[i]. readInt needs an address so it can write the value into the array, which is the copy-by-value plus pointer pattern.

Why pass n to addUp? Why not null-terminate the array?

When an array is passed to a function it decays to a pointer to its first element, so the length is lost. sizeof(arr) inside addUp would just be 8 (a pointer). So we pass the length separately.

We can't use a zero terminator because 0 is a valid value the user might type. A sentinel only works when that value can never appear in real data. For strings that's true, since '\0' is never part of text. For arbitrary ints it isn't, so addUp would stop at the first 0 the user entered.

Extra marks: %lu is for unsigned long, but addUp returns a signed long, so it should be %ld. Also, readInt takes an unsigned int* but receives an int*.

Q6 — Broken sizeof loop (assume 64-bit)

char* values[] = { "hello", "there", "now" };
int lengths[] = { 0, 0, 0 };
for (int i = 0; i < sizeof(values); i++) {
  lengths[i] = sizeof(values[i]);
}
Which lines are wrong, and how would you fix them?

Line 3, the loop condition: values is an array of 3 pointers, so sizeof(values) = 3 × 8 = 24 bytes, not 3 elements. The loop runs 24 times and writes past the end of lengths (buffer overflow, UB). Fix: divide by the element size.

Line 4, the length: values[i] is a char*, so sizeof(values[i]) is always 8 (pointer size), not the string length. Fix: use strlen from <string.h>, which counts chars up to the '\0'.

#include <string.h>
char* values[] = { "hello", "there", "now" };
int lengths[] = { 0, 0, 0 };
size_t count = sizeof(values) / sizeof(values[0]);   /* 24 / 8 = 3 */
for (size_t i = 0; i < count; i++) {
  lengths[i] = (int)strlen(values[i]);               /* 5, 5, 3 */
}

Using size_t i also avoids comparing a signed and an unsigned value.

Q7 — Stack, heap or data segment?

int main() {
  int p = 23;
  int *q = &p;
  *q = 3;
  char *t = "tasty";
  char *h = (char*)calloc(6, 1);
  memcpy(h, t, 5);
  free(h);
  return 0;
}
Are there any allocations on the stack? If so, where?

Yes. All four local variables: p (int, 4 B), q (int*, 8 B), t (char*, 8 B) and h (char*, 8 B). q points to p, so *q = 3 changes p to 3 without allocating anything.

Are there any allocations on the heap? If so, where?

Yes. calloc(6, 1) allocates 6 zeroed bytes on the heap, and h stores their address. memcpy copies t a s t y into the first 5 of them. free(h) gives them back.

Are there any allocations in the data segment? If so, where?

Yes. The string literal "tasty" is 6 bytes (t a s t y \0) in the read-only data segment. t only holds its address. (The constant 23 is encoded in the instructions, not stored as data.)

Why use calloc instead of malloc?

memcpy(h, t, 5) copies only 5 bytes and not the '\0'. Because calloc zero-fills, h[5] is already '\0', so h is a valid, terminated C string. With malloc, h[5] would be garbage, and using h as a string would read past the end (UB).

Also: the program needs #include <stdlib.h> and <string.h>, and should check h != NULL.

Q8 — Copy-by-value: minimise

void minimise(int a, int b) {
  if (a < b) {
    b = a;
  } else {
    a = b;
  }
}
Will this function work? Why or why not?

No. C is copy-by-value: a and b are local copies on minimise's stack frame. Assigning to them changes only the copies, which are destroyed when the function returns. The caller's variables never change, so the function has no visible effect.

How would you rewrite it to work? Do the rewrite.

Pass pointers (copies of the addresses), then dereference them to change the caller's variables:

void minimise(int *a, int *b) {
  if (*a < *b) {
    *b = *a;
  } else {
    *a = *b;
  }
}

/* call site */
int x = 4, y = 9;
minimise(&x, &y);   /* now x == 4, y == 4 */

The two heap allocations are never freed (memory leaks). Insert both just before return 0;, after the last use:

Last-minute cram list

Rules
  • All data has a place, a size, and zero is special
  • Copy-by-value only, so use pointers to modify the caller's variables
  • Breaking a rule means undefined behaviour (no requirements at all)
Memory
  • Stack: locals and params, compile-time size, freed on return
  • Heap: malloc/calloc/realloc, run-time size, you must free
  • Data segment: literals, constants and globals; literals are read-only; lasts the whole run
sizeof traps
  • sizeof(array) = total bytes
  • sizeof(pointer) = 8 on x64
  • Count = sizeof(a)/sizeof(a[0])
  • String length: use strlen, not sizeof
  • char c[]="hello" has 6 elements
Types
  • struct size = sum of members + padding
  • union size = largest member; all members at offset 0
  • enum values: 0, 1, 2, …
  • Defining a type reserves no memory
  • -> on pointers, . on values
Build
  • Preprocess → compile → assemble → link
  • Object code is not executable (it has relocation info)
  • Executable = library + entry point
  • <> searches system paths; "" searches local first
Errors
  • No exceptions: use errno and/or a special return value
  • Check malloc/calloc for NULL
  • Free every allocation, and only those
  • Use distinct error return codes for distinct failures

Two places where this sheet differs from the slides on purpose: (1) the slides write a constant pointer as int const *x, but correct C is int * const x; (2) one slide says globals go on the stack, but they go in the data segment.
